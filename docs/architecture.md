# How Print Buddy works

This file is ordered by area. `development.md` says where the files are and how to test. `adr/` says why some things are as they are.

This is the way of a Print Job. The phone picks or shares files. The app keeps them as the phone's copy and uploads them into a draft on the server. The options screen lays out the sheets with the layout module from the files' facts. On submit, the renderer builds one PDF with the same layout and the server sends it to CUPS. The job store keeps the job folder. The status screen asks the server, which asks CUPS, until the job has ended.

## Server

### Upload intake and drafts

- **File facts.** `FileFacts` in `shared/api.ts` is what the layout module and the renderer start from.
  - For a PDF, the facts are `pageCount` and `pages[]`. Each page has the size a reader shows, in points. That size is the part of the CropBox that lies on the page, with `/Rotate` applied. `shownPart()` in `server/source-pdf.ts` decides that part and the turn by the rules of pdf.js, for intake and for the renderer. Each page also has `content`: where it has ink, the smallest rectangle round everything that is not paper white, in points from the top left of the page as shown, or `null` for a page that is all white. `pageContents()` in `server/pdf-content.ts` finds it by rendering every page with MuPDF's `mutool draw` at 72 dpi, with anti-aliasing so that a hairline leaves a mark; paper white drawn over something is no ink. A page `mutool` renders at another size than `shownPart()` found, a `mutool` that is missing or fails, and the time limit of 30 s leave `content` out, and the page then counts as ink all over.
  - For a photo, the facts are `format`, the stored pixel `width` and `height`, and the EXIF `orientation`. The orientation is 1 to 8, and 1 when the photo has none. The pixel size is not turned, so for orientations 5 to 8 the upright photo is `height` × `width`.
- **Refusals.** A refused upload answers `{ refusal }` of type `Refusal`. The status is 413 for `too-large`, which also carries `limitMb`, 415 for `unsupported-type`, or 409 for the other three. The draft stays as it was. In the app, `addFile()` resolves with the facts or the Refusal and throws only for other failures. It takes a signal that stops it and an `onProgress` callback. The German texts are in `ui/src/screens/RefusalScreen.tsx`.
- **Upload limit.** `hono/body-limit` counts the bytes as they arrive. It answers 413 at `upload_limit_mb` plus 64 kB of multipart overhead, so the server never holds an oversized file. The server reads a file within the limit into memory once, at most `upload_limit_mb`. There is no streaming to disk and no `busboy`.
- **Drafts on disk.** A draft's files are `drafts/<draft-id>/<n>.pdf|jpg|png`, numbered in upload order. `intake.files(draftId)` gives the path and the facts of each. The list of drafts is in memory, and the server does not read it back after a restart.

### Print Options and the Printer

- **Submit.** The body of `POST /api/drafts/:draftId/submit` is the Print Options object itself, `SubmitRequest` in `shared/api.ts`. `parsePrintOptions` in `shared/print-options.ts` checks all of it: every field's values, a count of 0 to 50 for each item with at least one above 0, and an own size of at least 20 mm a side. Anything invalid gets a 400 `{ error: "invalid-options" }`, and nothing goes to CUPS. What needs the draft or the Printer's margins is `layOut()`'s to check, through the renderer, with the same answer. "Print Options that can't print" in the layout module below lists every case.
- **What CUPS gets.** `printer.printJob(pdf, options)` sends only `copies`, collated copies, `ColorMode`, `PageSize`, `Quality` and `MediaType`. It sends them as PPD keywords in `nameWithoutLanguage` values, `v.name(…)`, the way `lp -o` sends them. Our paper names are the PPD's `PageSize` names. Everything else in the Print Options has to be drawn into the PDF. The client in `server/printer/` is hand-written. See [ADR 0001](adr/0001-hand-written-ipp-client.md). Its codec was checked against a real cupsd 2.4.10.
- **Printable margins.** `GET /api/printer` answers `PrinterInfo`, which has `margins` per paper plus the Printer's `state`, `reasons` and `message`. Margins are in points, for the sheet in portrait, as `{ top, right, bottom, left }`. On the server the same values come from `printer.margins()`. The server reads them once, while it starts. A paper CUPS doesn't report gets 9 pt left and right and 12 pt top and bottom, with one warning in the log. When CUPS doesn't answer the state read, `state` is `unknown` and the margins are still there.

### The layout module

`layOut()` in `shared/layout.ts` decides where every page or photo sits, or says why the Print Options can't print. The renderer and the preview both call it, and add no geometry and no check of their own. No other function of the module lays out sheets, so no caller can skip the check. See [ADR 0002](adr/0002-one-layout-for-preview-and-print.md).

```ts
import { layOut, SHEET_SIZES } from "../shared/layout.ts"

const laidOut = layOut({
  source: { kind: "pdf", pages },      // page sizes in points as a reader shows them (the intake's facts)
  // or { kind: "photos", photos }     // per photo: stored pixel width and height, EXIF orientation
  options,                             // the Print Options
  sheet: SHEET_SIZES[options.paper],   // portrait, envelopes too
  margins,                             // the Printer's margins for that paper, in points
})
if (laidOut.reason === undefined) print(laidOut.sheets)
```

- Everything is in points. `options.items` has one `Item` per page of the PDF or per photo, in the file's order:
  - `count`, how often it prints on the sheets of one copy, 0 to `maxCount` (50). 0 leaves it out.
  - `turn`, a clockwise quarter turn on top of the turn the layout module gives it by itself.
  - `size`, an optional Füllen or Einpassen of its own.

  A placement's `ref` is the PDF page number counted from 1, or the photo index counted from 0.
- **Print Options that can't print.** `layOut` gives `{ sheets }`, or an `Unprintable`: a `reason` with what the options screen says it with. This is the one list of them, and it holds every reason Drucken is off because of the Print Options. They are checked in this order, and the first that applies is given:
  - `items-mismatch`: `items` hasn't exactly one entry per page of the PDF or per photo. The options screen takes it for "not laid out yet".
  - `format-on-pdf`: a Photo format for a PDF.
  - `own-size-too-small`: an own size under 20 mm a side, or without a number. While both sides are numbers above 0, it carries the `sheets` at the size typed, so the preview still draws the small slots.
  - `no-cells`: the layout has no Cells on the paper, a Photo format too large for it. It carries `otherLage`, "portrait" or "landscape", when the format fits only lying the other way, and `printable`, the printable area in whole mm, rounded down.
  - `nothing-printed`: every count is 0. It comes after the layout's reasons, so the screen can say what is wrong with the layout while nothing is printed.
  - `over-sheet-limit`: a Print Job of more than `maxSheets`, 100 sheets, copies included. It carries the `sheets` of one copy all the same, so the preview still shows them.

  `own-size-too-small` and `nothing-printed` are the rules of `parsePrintOptions`, `isOwnSide()` and `printsAnything()` in `shared/print-options.ts`, so the two can't disagree. `parsePrintOptions` still refuses them in a submit body or in storage. The renderer answers any reason with 400 `{ error: "invalid-options" }`, and the options screen turns it into German (see "Eigenes", "Nothing printed" and "The sheet limit" below). The app never submits one, because Drucken is unavailable then.
- `source` takes the intake's facts. Pass `PdfFacts` as it is, or `{ kind: "photos", photos }` with the `PhotoFacts` of the draft in order. `margins` is `PrinterInfo.margins[options.paper]`, or `printer.margins()[options.paper]` on the server.
- **Sequence.** The items in the file's order, each repeated `count` times next to itself (A A B B), fill the Cells sheet by sheet. A last sheet that isn't full keeps its empty Cells empty.
- **Cells.** `options.layout` is a grid, `{ kind: "grid", perSheet: 1 | 2 | 4 | 6 | 8 }`, or a Photo format, `{ kind: "format", format, lage, gap, cutLines }`. `cells(layout, sheet, margins, landscape)` gives its Cells in the order they fill, each a box on the sheet with its printable part, and whether the sheet is read `sideways`. `layOut()` places into them, and the sketches in the layout strip and in the confirmation draw them.
  - `perSheet: 1` is the whole sheet, and its printable part is the printable area. The other grids divide the printable area into equal Cells, so every Cell is all printable. They fill in reading order: 2 is 2 × 1 read in landscape, 4 is 2 × 2 read upright, 6 is 3 × 2 in landscape and 8 is 2 × 4 upright.
  - On a portrait sheet, which all four papers are, a grid read in landscape is `sideways`. The content lies on it turned 90° clockwise, and the first Cells lie along the sheet's right edge. The preview shows such a sheet turned 90° counter-clockwise, edge and all.
  - `landscapeFirst(source, items)` is true for a PDF whose first printed page is landscape as a reader shows it, its `turn` left aside. Then every grid is read the other way, the same Cells turned a quarter: 2 and 6 are read upright, 4 and 8 sideways. PDF pages never turn by themselves. Photos turn to the shape of their Cell at Einpassen and Füllen.
  - A Photo format's Cells are its slots, from `formatSlots()`: as many of its size as fit the printable area, 2 mm apart with `gap`, packed from the top left a row at a time. The sizes are `photoFormats` in `shared/print-options.ts`, or an own `{ w, h }` in mm. `lage` "portrait" and "landscape" turn every slot that way. "save" takes whichever holds the most: all upright, a block of upright slots with a strip of sideways ones below, all sideways, or sideways ones with an upright strip, the first of those on a tie. A format too large for the paper has no slots, and `layOut()` then gives the reason `no-cells`.
- **Inside a Cell.** Einpassen is the largest size inside the Cell's printable part, Füllen the smallest that covers the whole Cell, and a percentage scales from the natural size. An item's `size` replaces the Print size for that item. At a Photo format a percentage counts as Füllen. Position aligns the content to the Cell's printable part.
- `sheets` has one entry per sheet, so its length is the sheet count for one copy. `sheetCount(sheets, copies)` is the number of sheets of paper the whole Print Job takes. The options screen, the confirmation and the server all count with it. Each sheet has `placements`, `cutOff`, `emptySpace`, `sideways` and `cutLines`.
- `cutOff` means content lies outside the printable part of its Cell. For a photo that is the photo, so it is true at Füllen whenever the Printer has margins. For a PDF page it is the page's ink, `content` of its facts turned, scaled and placed like the page (`cutOff()` in `shared/layout.ts`): cut-off blank paper is no loss, a page whose `content` is `null` is never cut off, and a page without `content` counts as ink all over, like a photo. It is never set at a Photo format, where cropping to the slot is expected. `emptySpace` means part of the printable area stays empty. A job is cut off when any sheet is.
- `cutLines` are the slots of the sheet that hold a photo, when the format's `cutLines` is on, and empty otherwise. Empty slots on the last sheet get no lines.
- A placement's `left`, `top`, `width` and `height` are its box on the sheet, measured from the sheet's top-left corner. `rotation` is the clockwise turn of the upright content. `scale` × 100 is the effective percentage.
- **Renderer.** Write `matrix` as the `cm` operator and draw the page or photo. The matrix maps the content at its natural size, as stored, onto the sheet in PDF coordinates. EXIF orientation and every turn are already in it.
  - An image XObject is a unit square, so scale it by `photoNaturalSize(pixels)` first.
  - A PDF page's own `/Rotate` and CropBox are not in the matrix. `layOut()` gets the displayed page size, and the renderer adds the step from the embedded page to the displayed page.
  - Clip each placement to its `clip` box, its Cell or slot. Füllen would otherwise run into the next one.
  - Draw each box of `cutLines` as a hairline on top.
- **Preview.** Draw the upright picture into the box, turned by `rotation` and clipped to `clip`. An `<img>` already shows a photo upright, and pdf.js applies `/Rotate`.

### Renderer

- **What CUPS receives.** Submit calls `render(files, options, margins, dell, watch)` in `server/renderer.ts` and sends its `document`, never an uploaded file. The document is a PDF for the queue's driver, or HBPL for colour Print Jobs when Dell's engine is there. The result also has `sheets`, the number of sheets of paper the job takes, copies included. All photos of a draft go into one document and one Print Job. `watch.onProgress(sheetsDone, sheets)` reports each finished sheet, and aborting `watch.signal` stops the render between sheets, or between chunks of 64 rows for HBPL.
- **Colour Print Jobs through Dell's engine.** When `/share/print-buddy/dell-engine.json` is there (`dellEngineFile` in `server/config.ts`), `createApp` loads it once at startup. A missing or broken file is logged and leaves the PDF path. `dellRaster()` in `server/renderer.ts` renders every sheet as the Printer's full raster for the paper, `RASTERS` in `server/printer/hbpl.ts`: it takes each sheet's sRGB rows at 600 dpi and turns each into one byte of toner codes per pixel with `engine.dots()` in `server/dell-engine.ts`, which skips paper white. The rows come from one of two places:
  - **Photos.** `photoRows()` paints each row paper white with the photos on it; a dot belongs to the photo whose shown part holds its centre. `photoSampler()` traces the dot's centre back through the inverse of the placement's matrix to a pixel of the stored photo, which `sharp` has scaled to about one pixel per dot, upright for its EXIF orientation.
  - **PDFs.** The renderer builds the PDF the queue's driver would get, writes it to a temporary folder, and `pdfPageRows()` in `server/pdf-raster.ts` runs MuPDF's `mutool draw` on one sheet at a time, without anti-aliasing. It cuts or pads mutool's raster to `RASTERS[paper]`; the temporary folder goes once the raster is done or stopped.

  foo2hbpl2 packs the stream into HBPL (`foo2hbpl2` in `server/printer/hbpl.ts`). It cuts the unprintable edge of the paper off the full raster (`-u` and `-l` from `RASTERS[paper].clip`, 9 pt at the sides and 12 pt top and bottom for A4, the margins the layout uses), as the queue's wrapper does. `printer.printJob` sends it as `application/vnd.cups-raw` without PPD options or `copies`: the copies are in the data, each one rendered again. See [ADR 0007](adr/0007-colour-print-jobs-print-through-dells-engine.md).
- **Photos in a PDF.** Black and white photos, and colour photos without Dell's engine, are embedded as uploaded, JPEG or PNG. The queue's driver separates and screens them.
- **Form fields and annotations.** pdf-lib embeds only a page's content. So `drawAnnotations()` in `server/source-pdf.ts` first draws the annotations into the page. It draws each one's normal appearance, fitted to its rectangle, if the annotation is flagged for printing and not hidden. The preview asks pdf.js for the same set.
- **Print Options that can't print the draft's files** get a 400 `{ error: "invalid-options" }`, the same answer as malformed ones: `render()` returns `invalid-options` whenever `layOut()` gives a reason. The reasons are listed once, under "Print Options that can't print" in the layout module.
- **Cut lines.** The renderer draws each box of a sheet's `cutLines` as a 0.25 pt line in mid grey, into the PDF and, for Dell's engine, into the photo rows.
- **Photo memory.** The renderer handles photos one after the other. In a PDF it embeds each printed page or photo once, however often it is drawn. pdf-lib unpacks a PNG to raw pixels, about 360 MB for 4000×3000 on a Mac. So a large PNG batch is slow on the Pi. This was not measured there. Through Dell's engine, a full-page photo peaks at about 270 MB and takes about 4 s on a Mac. A PDF page through Dell's engine takes about 1.7 s on a Mac; mutool needs about 140 MB for an A4 page at 600 dpi.

### Submit and the job folder

- **Job folder.** `<jobs dir>/<date>_<job-id>/` holds `upload-1.pdf`, `print.pdf` and `job.json`. In place of `upload-1.pdf` it can hold `upload-1.jpg`, `upload-2.png`, … in upload order. In place of `print.pdf` it holds `print.hbpl` when the job went out through Dell's engine. The date is the UTC day the job was sent. No file carries the name it had on the phone.
- **`print.pdf` or `print.hbpl` is what CUPS got.** Submit in `server/http/drafts.ts` holds the rendered bytes in one variable, `document`. It passes that variable to both `printer.printJob(document, options)` and `jobs.add({ …, document })`. Keep it that way, so the folder can't hold anything other than what was printed.
- **Submit uses up the draft.** After CUPS has accepted the job, `jobs.add` moves the uploads into the job folder and `intake.discard(draftId)` forgets the draft. A second submit of that draft gets a 404. To print again, upload into a new draft, as "Nochmal drucken" does.
- **A submit that can't be sent** answers `SubmitFailure` from `shared/api.ts`. The status is 502 for `cups-unreachable` or `cups-rejected`, and 500 for `render-failed`. No Print Job is created and the draft stays, so the same submit can be repeated. The cause goes to the server log.
- **Progress and stop.** While a submit runs, `GET /api/drafts/:draftId/progress` answers its `SubmitProgress`: `preparing` with `sheetsDone` of `sheets`, then `sending` once CUPS gets the job. `POST /api/drafts/:draftId/stop` aborts the render while it is `preparing` and answers 204. The submit then answers 409 `{ error: "stopped" }`, with no Print Job and the draft unchanged. In `sending` the stop answers 409 `{ error: "not-stoppable" }`, because the job may already be in CUPS: it is cancelled as a Print Job instead. The running submits live in memory in `server/http/drafts.ts`, one per draft. A second submit of a draft while one runs gets 409 `{ error: "already-submitting" }`.
- **After CUPS has accepted the job, submit answers with the Print Job whatever else fails.** See [ADR 0004](adr/0004-accepted-job-is-always-answered.md). A job folder that can't be filled, a `job.json` that can't be written and a draft that can't be deleted are logged and not thrown. The job's status stays readable from memory until the server restarts.
- **`job.json`** is the `PrintJob` record of `server/job-store.ts`. Its fields are:
  - `id`, `cupsJobId`, `sentAt`, `endedAt` and `sheets`
  - `file`, with the type, size and page or photo count of what was uploaded
  - `options`, the Print Options
  - `details`, what CUPS last said
  - `cancelled`

  The two times are ISO 8601 text in the file and millisecond numbers in the record. A new field of `PrintJob` lands in the file by itself. It must never be a name of a person, an email or a file name. See [ADR 0005](adr/0005-nothing-personal-is-kept.md).
- **Job store.** `await jobs.update(job, changes)` gives the changed record. The store never changes a record in place. It applies the changes to the record as the store holds it now, so an older copy in the caller's hand can't bring old values back. `details`, `endedAt` and `cancelled` are the fields that change after `add`. The store writes the file at submit and whenever `jobs.update` changes something. A status read that learns nothing new writes nothing.
- **After a restart.** `openJobStore` reads every `job.json` back, so `GET /api/jobs/:jobId` works as before and goes on asking CUPS. It skips a folder whose `job.json` can't be read, with a warning.
- **Cleanup.** `startServer` runs it once before it listens and then every hour. `RunningServer.cleanup()` is the same function. It has two parts, each in the module that owns the folders:
  - `jobs.cleanup()` deletes job folders more than 7 days after `sentAt`. A folder without a readable `job.json` counts from the end of the day in its name.
  - `intake.cleanup()` deletes drafts more than 1 hour after they were created, and every draft folder that has no draft. That covers what an earlier run of the server left behind, since nobody can submit those any more.
  - Both look only at entries named like their own folders. Those are `<date>_<uuid>` in the jobs directory and `<uuid>` in `drafts/`. Anything else a person puts there stays.

### Job status

- **Reading a Print Job.** `GET /api/jobs/:jobId` answers `JobStatus` from `shared/api.ts`. It has `state`, `reason`, `details`, `cupsJobId`, `sentAt`, `endedAt` and `sheets`, and for the report `file` and `options`.
  - `state` is a `ScreenState` key, one of `waiting`, `printing`, `done`, `cancelled` and `error`. The German words are in `ui/src/state-words.ts`.
  - `reason` is a German sentence, or null when there is nothing to explain.
  - `details` is what CUPS said. It has `jobState` as the IPP keyword, `jobStateReasons`, `printerStateReasons` from `job-printer-state-reasons`, and `printerMessage` from `job-printer-state-message`.
- **Each read asks CUPS** with Get-Job-Attributes, until the job has ended. The first read that sees the end sets `endedAt` from the server's clock, so it can be up to one poll late. After that the server answers the stored state and doesn't ask CUPS again. When CUPS can't answer, or no longer knows the job, the read answers the last state seen, with a warning in the log. A read looks at the record again once CUPS has answered. If a cancel or another read saw the job end in the meantime, that result stands and the read drops the late answer.
- **Status mapper.** `mapStatus(details, cancelledByPrintBuddy)` in `server/status-mapper.ts` is the one place that decides state and reason. A `processing` job is Wartet when its printer message says the Printer isn't connected yet, per `notConnectedMessages`. `processing-stopped` is Wartet too.
- **Reasons.** `reasonTexts` maps reason keywords to German sentences. The mapper looks through the job's reasons, then the Printer's. It takes the first keyword it knows, with a trailing `-report`, `-warning` or `-error` removed. After that it checks the backend message against `messageTexts`.
- **Which states have a reason.** Fehler always has one. It is the known reason, or "Beim Drucken ist ein Fehler aufgetreten.", or the sentence for a job somebody else cancelled. Wartet and Wird gedruckt have one only when CUPS names a known reason. Fertig and Abgebrochen have none.
- **Cancel.** `POST /api/jobs/:jobId/cancel` answers the new `JobStatus`, or 409 `{ error: "not-cancellable" }`. A cancel is allowed while the job runs, as Wartet or Wird gedruckt; what the Printer already has may still come out. CUPS marks every cancelled job the same way, so the job store's `cancelled` flag records Print Buddy's own cancel. The server sets the flag before it asks CUPS and takes it back when CUPS refuses. So a status read that overlaps the cancel never takes it for somebody else's. `printer.cancelJob()` resolves false when CUPS refuses with `IppRefusal`, which is a bare HTTP status or an IPP error status. It throws only when CUPS can't be reached.
- **Sheet count.** Submit sets `sheets` to `sheetCount()` of the layout module. That is the number of sheets in the rendered PDF times `copies`, so it follows `items` and the layout.

## App

### Screens and the phone's copy

- **The phone's copy.** `phoneFiles` in `ui/src/phone-files.ts` is the one place that keeps the files of the job in progress. Its functions are `keep(files)`, `held()` and `clear()`. It is one record in IndexedDB, in database `print-buddy` and store `phone-files`. So it survives a full page load, and it works over plain HTTP too. The service worker puts a share there, and `pick()` puts picked files there. `beginUpload()` in `App.tsx` starts every upload. A share, "Datei auswählen", "Nochmal drucken" and "Erneut versuchen" all upload what the store holds. No screen state carries files from screen to screen, except the options screen, which shows them. See [ADR 0003](adr/0003-files-stay-on-the-phone.md).
- **When the copy goes.** `leaveJob()` in `App.tsx` clears the phone's copy. It does so on "Schließen", on "‹ Zurück", and when an upload finds the store empty. A Refusal clears it, because nothing prints. Opening the app without a share clears it, because no job is in progress then. "Drucken hat nicht geklappt" keeps it until "Schließen".
- **New ways in and out.** Every new way out of a job has to call `leaveJob()`. Every new way in has to go through `phoneFiles.keep()` and `openHeld()`.
- **"Datei auswählen"** is `ui/src/controls/FilePicker.tsx`, the one file picker. The Start, Refusal and "Bitte nochmal teilen" screens share it.

### Start screen

- `canReceiveShares` is true where the browser has a service worker. Over plain HTTP it is false and the share hint is not shown.
- The logo, the name and "PDFs und Fotos vom Handy drucken" sit in the middle. "Datei auswählen" is the last element, at the bottom within reach of the thumb with the phone in one hand. It is not sticky. When the screen is too short, for example with a large font, the page scrolls, and nothing lies over "Bericht kopieren". On screens up to 640 px tall the logo is 80 px instead of 112.
- **Last job.** `lastJob` in `ui/src/last-job.ts` keeps `{ jobId, cupsJobId }` of the last submit in `localStorage` under `print-buddy.last-job`. `print()` in `App.tsx` writes it. `LastJobLine` reads the job once when Start shows, as "Letzter Druck: {Zustand}" with the report button. A 404 forgets the job, because the job folder is gone after 7 days. Any other failure shows "Letzter Druck: unbekannt" and still offers the report.

### Share-to-print

- **The way of a share.** The manifest, `ui/public/manifest.webmanifest`, tells Android to POST to `/share-target`. The service worker answers that POST itself with `receiveShare()` in `ui/src/share-target.ts`. It puts the files into the store, then answers with a 303 to `/?shared=1`. `App` sees `shared` in its address, shows `OpeningScreen`, removes the parameter and calls `openHeld()`. The path, the form field and the parameter are constants in `shared/share-target.ts`, and a test keeps the manifest equal to them.
- **Until the options screen opens with a share,** `OpeningScreen` shows the app's name and "Wird geladen …". It shows them while the browser reads the files. For a file the browser can't read, it shows them until the server has the file.
- **A share without files** ends on "Bitte nochmal teilen". This happens with a known Chrome bug, or with a body Chrome can't read.
- **`/share-target` on the server** answers every method with a 303 to `/?shared=lost` and keeps nothing. A request reaches it when no service worker took the share, and when the browser comes back to that address from the Cloudflare login. The app then shows "Bitte nochmal teilen" and clears the phone's copy. The address has to say so, because the phone may still hold the files of an earlier job, and they must not open in place of the lost share.

### Service worker and updates

- **Service worker.** The `serviceWorker()` plugin in `vite.config.ts` builds `ui/src/sw.ts`. It runs a second build, after the app, into one self-contained `/sw.js`. The plugin fills in `__APP_SHELL__` with the list of files the app build wrote and a hash over their contents. Those files are the page and everything under `/assets`. `handledBy(request)` decides who answers: `share`, `shell` or `network`. `shell` answers from the cache `print-buddy-shell-<hash>`. Only `/` and `/assets/*` ever come from the cache. API calls, `/login`, `/sw.js`, the manifest and the icons always go to the server. A file that is loaded later, such as the pdf.js worker, is in the shell as long as Vite emits it under `/assets`.
- **Updates.** The browser installs a changed `/sw.js` in the background, and the new worker waits. `startAppUpdate()` in `ui/src/app-update.ts` tells it to take over only while no job is in progress. It does so when the app opens on Start, when the new version finishes installing while Start shows, and from `leaveJob()`. `App` reports the job with `update.setJobInProgress()`. The worker takes over only if this window is the only one open. Otherwise it waits until all are closed. After the take-over the page reloads once, unless a job has begun in the meantime. The person hears about it twice, as an `UpdateNote` over the top of the screen that goes by itself after 6 s and lets taps through. The take-over leaves a mark in `localStorage` before it reloads; the page that opens takes the mark away and says "Print Buddy wurde aktualisiert." (`update.updated`). While a job keeps a new version waiting, `startAppUpdate(onHeldBack)` calls back once and the app says that it loads after the job. The first update into a version that has these notes can't show the first one: the page that handles that take-over is still the old code.
- **Files pdf.js fetches.** `scripts/pdfjs-assets.ts` copies `wasm`, `standard_fonts`, `cmaps` and `iccs` from `node_modules/pdfjs-dist` into `ui/public/pdfjs`. They are 4 MB and not in git. Vite takes them into `dist/ui/pdfjs`. pdf.js fetches one from `/pdfjs/…` only when a PDF needs it, for example for a scanned page in JBIG2 or JPEG 2000, or for a font that isn't embedded. These files are not in the app shell and always come from the server. `pnpm build` and `pnpm dev` run the script first. A bare `vite build` leaves the files out. The Dockerfile runs `pnpm run build`.
- **Icons.** `ui/public/icon.svg` and `icon-maskable.svg` are the sources. `ui/src/controls/Logo.tsx` draws the same printer on the Start screen, inline so that it shows from the cache too. `print-buddy/logo.svg` puts it beside the name for the Home Assistant app page. Change all four together. Make the PNGs with `rsvg-convert -w 512 -h 512 icon.svg -o icon-512.png`, and with 192 for the small one. In `print-buddy/`, make `icon.png` at 128 from `ui/public/icon.svg` and `logo.png` at 500 × 200 from `logo.svg`. Home Assistant shows the icon in the app store and the logo on the app page. Never rename the manifest, `/sw.js` or an icon. See [ADR 0006](adr/0006-fixed-addresses-for-the-installed-app.md).
- **Fonts.** Nunito (all text), Permanent Marker (big headings) and Caveat (sticky notes) are self-hosted as latin-subset `woff2` files in `ui/src/fonts`, which Vite emits under `/assets`, so the service worker caches them. Their licenses (SIL OFL for Nunito and Caveat, Apache-2.0 for Permanent Marker) are in `ui/public/licenses` and go into the build beside the app. Add a font only with its license text.
- **Paper colour.** `#fbf8f0` is `--color-white` in `ui/src/app.css`, the `theme-color` in `ui/index.html`, and `background_color` and `theme_color` in `ui/public/manifest.webmanifest`. Change all of them together; the sheet in the preview and the thumbnails stay pure white (`bg-paper`).

### Upload behind the options screen

- **Upload on pick.** `openHeld()` in `App.tsx` starts the upload with `startUpload()` in `ui/src/upload.ts`, which makes a new draft and sends one file per request in order. At the same time it reads the files' facts in the browser with `readFacts()` in `ui/src/file-facts.ts`. The options screen opens as soon as the facts are read, usually well before the upload is done. Some files the browser can't read. Those are files that aren't PDF, JPEG or PNG by their head, and PDFs pdf.js can't open. Such a file waits for the server, which then refuses it or sends its facts.
- **Facts in the browser.** A PDF's page sizes come from pdf.js through `pageSizes()` in `ui/src/pdf-preview.ts`. It takes the viewport at scale 1, without `/UserUnit`. These sizes match `shownPart()` in `server/source-pdf.ts`. They were checked against intake for plain pages, `/Rotate` 90 and 270, CropBoxes partly outside the MediaBox and a 45° `/Rotate`. A photo's facts come from `photoFacts()` in `shared/file-header.ts`, the same function intake uses, with `exifr` in the browser too.
- **The server's facts count.** Once the upload is done, `OptionsScreen` gets the server's facts in place of the browser's. Only they have `content`, so until then a PDF is cut off wherever it is larger than the printable area, and the warning can show for a moment at Füllen. Drucken is unavailable until then and reads "Wird hochgeladen … n %". The percentage is the share of all files' bytes, at most 99 % until the server has answered for the last file. So the confirmation's sheet count and everything sent are laid out from the server's facts. If the two disagree on the number of pages or photos, every one the server found prints once.
- **The options screen state** in `App.tsx` holds `files`, `facts` and the running `upload`. `files` is the phone's copy, in shared or picked order. `facts` is in the same order and holds the browser's facts until the server's arrive.
- **Endings of the upload.** A Refusal shows the Refusal screen whenever it arrives, on whatever screen. A 401 shows "Anmeldung abgelaufen", and the files stay on the phone. Any other failure while the options screen shows leads to "Drucken hat nicht geklappt" with `printed: false`. "Erneut versuchen" then opens the options screen again with the same Print Options and a new upload, and prints nothing by itself. After Drucken, "Erneut versuchen" sends again.
- **"‹ Zurück"** on the options screen calls `leaveJob()`. It aborts a running upload request, and an answer that still comes changes nothing. Then it clears the phone's copy and goes to Start.

### Options screen

- **Top to bottom**, the screen has these parts:
  - "‹ Zurück" with the file name
  - Preset chips
  - "Einstellungen" beside Ansicht
  - preview
  - one row of fixed height: the stepper, or the bar of the page or photo picked in the preview
  - the layout strip
  - Breite and Höhe, at Eigenes
  - "Wie oft": the thumbnails with their counts, or one stepper for a single page or photo
  - at a Photo format: "Lage der Fotos", "Abstand zum Schneiden" and "Schnittlinien"
  - "Größe für alle" beside the Position grid
  - the cut-off warning
  - Drucken, with the reason under it when the Print Job is over the limit or the format doesn't fit
- **By width.** A phone gets one column, at most 480 px wide. From 768 px the column is 576 px wide. From 1024 px `<main>` is a grid of two columns: the preview, with "Einstellungen", Ansicht and the row under it, sticks on the left, and the rest scrolls on the right, with Drucken sticky at the bottom. `App.tsx` widens its shell for the options screen only. The preview's height before zooming is the CSS variable `--sheet-height` in `Preview.tsx`: 44 % of the screen on a phone, half from 768 px and the screen less 10 rem from 1024 px.
- **State.** `OptionsScreen` keeps an `Editing` of the Print Options editor, `ui/src/print-options-editor.ts`, in one signal: the Print Options, the facts they are laid out for and the own size Eigenes stands for. The editor is plain TypeScript without Solid, and owns every edit of the Print Options and everything that follows from them:
  - `edit(editing, change)` takes an `Edit` and gives new Print Options and which sheet to show: the first one, or the sheet of a `ref`. The screen's `change()` applies both. An edit names a page or photo by its `ref`, and only the editor turns a ref into an item. The edits are Repeats and "Alle gleich", a turn, an item's own size, "Größe für alle", Position, Pan, the layout, Lage, gap and cut lines, the own size, the detailed controls, picking a Preset and the server's facts.
  - The Pan rule of `GLOSSARY.md` is written once, in `dropsPans()`. A Preset sets its seven fields and drops the Pans; Repeats, turns and each item's own size stay. Facts from the server that count the pages or photos differently print every one once, from the first sheet.
  - It keeps the own size while another layout is chosen, and the Photo format defaults: a format chosen from a grid or a percentage moves the Print size to Füllen, and Lage, gap and cut lines carry over from format to format. `formatSwitches` tells the strip what a format chosen now starts with.
  - `derive(editing, margins)` gives what follows: `unprintable`, the reason of `layOut()` why the Print Options can't print, the sheets the preview draws, `refs`, which pages or photos print, an item and its size by ref, the percentage on a sheet, the mixed sizes, cut-off, the limit and the confirmation's numbers.

  The screen keeps the view state: zoom, which dialog is open, the picked page or photo and the sheet shown, and all German text and the JSX. It reports every change with `onChange` and hands the Print Options to `onPrint`. A new file starts with `startEditing()` from the default Preset of its file type and the `facts` prop: every page or photo once, unturned. After a login, `initial` replaces the Preset, as "Expired login" below describes. The editor's tests are tables of cases in `ui/src/print-options-editor.test.ts`. `Stepper`, `ChoiceGroup` and `ToggleChip` are in `ui/src/controls/`. `ChoiceGroup` is a `radiogroup` of chips whose values are strings or numbers, and `ToggleChip` is a `switch`. Tests find them by role and German name.
- **One layout for the whole screen.** `OptionsScreen` reads the margins with `readPrinter()`, and reads them again every 2 s for as long as that read fails. `derive()` calls `layOut()` in the screen's one memo, `derived`, and its `sheets` are what the preview draws. The preview, the percentage in "Größe für alle", the cut-off warning, the stepper and the confirmation all read `derived`. None of them computes a size or a place. Drucken is on only while `unprintable` is empty. `ownProblem()` turns a reason into the sentence under Breite and Höhe, and `underDrucken()` gives the one line under Drucken: the sheet limit, then too many photos added, then a Photo format the paper can't take. The screen asks nothing else to explain one. Until the margins are there, nothing is laid out, though an own size under 20 mm already says so, and `items-mismatch` counts as not laid out yet: the paper is empty, Drucken is off without a sentence, and the − / + buttons are left out. Over the sheet limit, and at an own size under 20 mm with sides above 0, the sheets still show; for any other reason there are none. The limit is counted from those sheets, so an own size under 20 mm says both.
- **Layout of the screen.** "Größe für alle" and the smaller Position grid sit side by side, each with a small caption. "Größe für alle" is `PrintSize`, with the compact `ChoiceGroup` and `Stepper`. The Position grid has 32 px spots. Controls on the screen are 40 px high. The Drucken bar is the last element of the controls, sticky at the bottom with a top border, so at the end of the page nothing lies under it. At 360 px the print size chips leave about 20 px to the grid. A wider label there needs a new look at this row.
- **Größe für alle.** PDFs get Einpassen, Füllen and 100 %, and − and + that move in steps of 5 from the percentage shown and switch to a percentage. The range is 10 to 400 %, taken from the prototype. Photos get Füllen, Einpassen and 100 % without steps, and at a Photo format only Füllen and Einpassen. A format chosen from a grid, or from a percentage, starts at Füllen, its default; between formats the size stays. A choice here takes away the sizes pages or photos have of their own. While the printed ones differ, no chip is marked, and each size in use carries a dot. `100 %` is marked only at exactly 100. The percentage shown is read off the first page or photo on the shown sheet without a size of its own.

#### Preview

- **The preview** is `ui/src/controls/Preview.tsx`, the `region` named "Vorschau". It gets one `Sheet` of the layout module, the paper size and the margins. It only turns points into percent of the sheet. For each placement it draws the `clip` box, in it the placement's box, and in that the upright picture turned by `rotation`. It draws every placement of the sheet as the layout module puts them, and the sheet's `cutLines` as thin lines. A `sideways` sheet is shown turned 90° counter-clockwise, edge and all.
- **Which sheet.** `shown()` in `OptionsScreen` is the sheet the person stepped to, or the one an edit sent the preview to.
- **Picking.** A tap on a page or photo in the preview picks it: a pointer that went up less than 10 px from where it went down. Every appearance of it on the sheet gets an outline, and `ItemBar` takes the place of the stepper under the preview. The bar is the `toolbar` named "Seite 2" or "Foto 2", with "Nach links drehen", "Nach rechts drehen", its size and "Schließen". The turns add to the item's `turn`. The size button makes Füllen into Einpassen and anything else into Füllen, for that item only. A tap beside the content, "Schließen", or a touch on any control outside the preview and the bar ends it; those two carry `data-picks`. A page or photo turned by hand shows "↻" in a corner, named "Seite 2 von Hand gedreht".
- **The pictures.** `ui/src/controls/PdfPage.tsx` draws one PDF page through `openPdf(bytes)` and `renderPage(pageNumber, longSide)` of `ui/src/pdf-preview.ts`. The preview uses it with `fit="fill"` and a label. The thumbnails use it with `fit="contain"` at 176 px. pdf.js draws with `intent: "print"`, so a form field or an annotation shows exactly when the server's renderer draws it too. For photos, the preview and the thumbnails show the phone's copy from the `files` prop through object URLs. The screen revokes the URLs when it goes. An `<img>` applies the EXIF orientation itself.
- **Black and white, paper, edge.** Black and white is a CSS `grayscale` filter on the picture. The sheet has the paper's aspect ratio and always fills the same panel, so A4 and A5 look alike except for the wider edge. The unprintable edge is a dashed frame at the margins with a pale veil outside it. The warning is about content under the veil or beyond the paper.
- **Ansicht**, `ViewZoom`, is 100, 150, 200 or 300 %, on the screen only. The panel then scrolls in both directions. A PDF page is drawn again with more pixels, with a long side of 1500 px × zoom and at most 3000.
- **Swipe.** `Preview` takes `index`, `count` and `onStep` beside the sheet. It steps on `pointerup` when the primary pointer moved at least 50 px sideways, and more sideways than up or down. It does nothing at the first or last sheet, and nothing unless Ansicht is 100 %.
  - At 100 % the panel has `touch-action: pan-y pinch-zoom`. So the page scrolls vertically over it and Chrome hands the sideways move to the app. When the browser takes a gesture over for scrolling, it sends `pointercancel`, which drops the swipe.
  - Zoomed in, `touch-action` is `auto` and a drag pans the panel.
  - A swipe slides the new sheet in by 24 px over 150 ms with the Web Animations API, except with reduced motion. The sheet is drawn at once.
- **Why no CSS carousel.** Scroll snapping would need every sheet drawn side by side, but pdf.js draws one at a time. It would also fight with the sideways scrolling of a zoomed preview.

#### Layout strip, Wie oft and stepping

- **Layout strip.** `LayoutStrip` is the `radiogroup` named "Aufteilung", in a `FadingRow`: a row that scrolls sideways without a scrollbar, fades the edge with more beyond it, scrolls with a mouse wheel and centres the marked entry when it appears. Its tiles are `gridChoices`, Normal and 2× to 8×, and for photos `formatChoices()`, 10×15, 9×13, 13×18, Passbild and Eigenes. Each tile sketches the Cells `cells()` gives on the paper; Eigenes shows "mm". A format that doesn't fit the paper is greyed out, except Eigenes, whose inputs say what doesn't fit. A tap hands the editor the tile's `LayoutPick`: a grid, a format by name, or Eigenes. A new layout goes back to the first sheet, and a new format keeps Lage, Abstand and Schnittlinien.
- **Eigenes.** Breite and Höhe are in mm. Under 20 mm they say "Breite und Höhe mindestens 20 mm.". A size that only fits lying the other way says "Passt nur mit Lage Alle hoch.", and one that fits no way "Zu groß für A4: höchstens 203 × 288 mm.", with the `printable` size in whole mm of the `no-cells` reason. Drucken is off meanwhile. The screen keeps the own size while another layout is chosen. A named format that doesn't fit a paper chosen after it says "13×18 passt nicht auf Umschlag DL." under Drucken.
- **Wie oft.** `Thumbnails` in `ui/src/controls/Thumbnails.tsx` is the `section` named "Wie oft". "Alle gleich" with "Alle seltener" and "Alle öfter" sits above the row, the `group` named "Seiten" or "Fotos" in a `FadingRow`. Each picture is a button named "Seite 2" or "Foto 2" with `aria-pressed`. A tap leaves it out ("aus") or brings it back once. "Seite 2 seltener" and "Seite 2 öfter" under it count it down to "aus" or up to 50. From mixed counts, the first tap of "Alle gleich" brings every printed one to the highest; then they move together, never below 1. A PDF of more than 30 pages gets pictures that only switch on and off, so a page brought back there prints as often as the others. A picture shows the page or photo upright as it is in the file, in grey when black and white is chosen, with its count as a badge. PDF pictures are drawn once they scroll into view.
- **Stepping.** `SheetSteps` shows "‹ Seite 3 · 2/4 ›" for a sheet with one page, "Seiten 3 und 4 · 2/2" for two different pages, "Foto 2/3" for one photo and "Blatt 2/4" for anything else. The numbers are which sheet of how many, for one copy. It is the `status` named "Blatt in der Vorschau", and the buttons are "Vorheriges Blatt" and "Nächstes Blatt". The screen keeps the step past the end and clamps it when read, in `current()`. So leaving out the last page shows the sheet before it. Bringing a page back shows the sheet of its first appearance.
- **Nothing to choose, nothing shown.** With one page or one photo, "Wie oft" is one `Stepper`, 1 to 50, and `refs()` in `OptionsScreen` has one entry. `SheetSteps` is left out whenever the layout has exactly one sheet. With nothing printed it still shows.
- **Nothing printed.** When every page or photo is "aus", the status reads "Keine Seiten ausgewählt" or "Keine Fotos ausgewählt". The Drucken button is disabled and reads "Keine Seiten gewählt" or "Keine Fotos gewählt".
- **The sheet limit.** A Print Job over 100 sheets, copies included, disables Drucken, and "Höchstens 100 Blätter pro Druck." stands under it.

#### Details and confirmation

- **Detailed controls.** `OptionsDrawer` is a sheet at the bottom edge, the dialog named "Einstellungen". It holds Kopien, Farbe, Papier, Qualität, the Preset actions and "Fertig". "Einstellungen" beside Ansicht and the last Preset chip open it. Every change applies at once and the preview behind follows. There is nothing to undo. A new option that is not on the spec's list for the screen goes in here as one more row.
- **Confirmation.** Drucken on the screen only opens `Confirmation`, the dialog named "Jetzt drucken?", a panel at the bottom edge so its buttons are within reach of the thumb. "Abbrechen" closes it and leaves the Print Options untouched. Its Drucken calls `onPrint` and leads straight to the sending screen, and `print()` in `App.tsx` ignores a second tap. From top to bottom it shows:
  - The sheets for all copies as a big number, the `output` named "Blätter insgesamt", red over the limit, with "1 Kopie" or "3 × 2 Kopien" under it. Beside it, a sketch of the layout's Cells and its name: "Normal", "8×", "10×15" or "Eigenes 60 × 90 mm".
  - The pages or photos, the list named "Seiten" or "Fotos", each with "2×" or "aus". A PDF of more than 30 pages gets one line instead, such as "37 von 40 Seiten, je 1× · 3 aus".
  - Every setting in use as a `DisplayChip`, the list named "Einstellungen": colour, paper, quality, the size, Position at a grid or the Lage, Abstand and Schnittlinien at a format, and the copies from 2. The size reads "Einpassen (97 %)", or "Größe je Seite" and "Größe je Foto" while the printed ones differ.
  - One line, the `status` named "Hinweis": "Höchstens 100 Blätter pro Druck." with a `StopIcon`, in red, with Drucken off, else "Teile des Inhalts werden abgeschnitten." with a `WarningIcon`, on a sticky note, when a sheet is cut off, else nothing. The icons are drawn in `controls/Icons.tsx`, not glyphs from the font, which some phones draw as an empty box.
  - Abbrechen and Drucken.

  Every part keeps its height, so the panel is as tall for every Print Job. It has no heading and no file name.
- **Nothing is computed there.** Its numbers are `confirmation()` of the editor's `derive()`, for the sheet in the preview, handed to `Confirmation` whole. The sheet count is `sheetCount()` of the layout module over the sheets and the copies, and the limit is `maxSheets` over that count, as `layOut()` gives `over-sheet-limit`. The sketch is `cells()` for the layout and paper. The percentage is the one "Größe für alle" shows, and the warning is the same flag. The server's `sheets` is the same function over the same layout, so the two can't differ. Drucken on the screen is unavailable until the margins have arrived, so the confirmation always has its numbers.
- **No "Drucken (n Kopien)"** on the button, which the prototype had. The copies are in the confirmation.
- **Words.** `ui/src/job-text.ts` has the names of papers, qualities, Positions, sizes (`sizeNames`), Lagen (`lageNames`) and formats (`formatNames`), `layoutName()` for "Normal", "8×", "10×15" or "Eigenes 60 × 90 mm", `itemName()` for "Seite 2" and "Foto 2", `printedNumbers()` and `ranges()` for "1-3, 5", `counted()` for "1 Seite" and "3 Seiten", and `printSizeText()`. Every control, the confirmation and "Nochmal drucken?" take them from there.
- **Dialogs.** `Dialog` in `ui/src/controls/` is the dimmed backdrop with a panel, in the middle or at the bottom edge. A tap beside the panel and Escape close it, and it takes the focus when it opens. Whoever opens a dialog makes the screen behind it `inert`. `OptionsScreen` keeps which dialog is open in `over` and sets `inert` on its `<main>`.

#### Presets

- **Where.** `ui/src/presets.ts` has the built-in Presets, the `PresetValues` type and `createPresets(kind)`, which reads and writes browser storage. `PresetValues` holds the seven fields a Preset stores. `PresetChips` and `PresetActions` under `ui/src/controls/` are the two parts on the screen. Both take the Print Options and call `onPick`. `OptionsScreen` then calls `presets.pick()`, for which chip is marked, and the editor's `preset` edit.
- **A new field in the Print Options.** If a Preset should store it, add it to `PresetValues`, to `sameValues` and to `save` in `presets.ts`, and to the built-ins. Presets already store and compare Print size, Position and the layout, so their controls only have to send an edit to the editor. `items` belongs to the file, and a Preset never touches it. A stored Preset from before `layout` fails `parsePrintOptions` and is dropped on load.
- **File type.** `OptionsScreen` takes `kind: FileKind`, which is `"pdf" | "photo"` in `shared/api.ts`. `fileKind(facts)` in `presets.ts` is the one place that decides it. It takes the `kind` the server found for the first file of the Print Job, because a draft never mixes the two. `App` calls it. The kind picks the chips, the default Preset and which star is set. `OptionsScreen` reads it once, so a new file gets a new `OptionsScreen`.
- **Starting options.** A new file starts from the starred Preset of its type, with every page or photo printed once and unturned. Nothing from a Print Job is written to storage, so the next file can't inherit it.
- **Chips per type.** PDFs get Dokument Farbe, Dokument s/w and Umschlag DL. Dokument Farbe is the built-in default and comes first. The two documents start at Füllen, because a PDF is made to be printed: an A4 page prints at its own size, and only ink in the unprintable edge is cut off. Umschlag DL, and the photos, start at Einpassen. Photos get Foto and Foto s/w Toner sparen. An own Preset belongs to the file type it was saved for.
- **Which chip is marked.** The marked chip is the Preset whose seven fields all equal the Print Options. If several are equal, it is the one tapped or saved last, else the first in chip order. If none is equal, the last chip reads "Eigene" with a `PencilIcon`. Otherwise it reads "Eigene …". Tapping that chip opens the detailed controls, where the Preset actions are too. The starred Preset's chip, and the disabled "Standard" button, carry a `StarIcon`. The star is a picture, so the chip also has the description "Standard" for screen readers, and tests read the star from it.
- **Preset row.** `PresetChips` is the `radiogroup` named "Voreinstellung" in a `FadingRow`, as the layout strip. It centres the marked chip when the screen opens.
- **Storage.** Presets live in one `localStorage` key, `print-buddy.presets`, as `{ own: Preset[], defaults: { pdf?: id, photo?: id } }`. Entries that don't pass `parsePrintOptions` are dropped on load. A starred id that no longer exists falls back to the built-in default.

### Sending, status screen and failures

- **Buttons at the bottom.** The sending, status, "Drucken hat nicht geklappt", Refusal, "Bitte nochmal teilen" and "Anmeldung abgelaufen" screens are built on `ThumbScreen` in `ui/src/controls/`. It puts the content at the top and the `actions` at the bottom, the main one last and nearest the thumb with the phone in one hand, as "Datei auswählen" on Start. It is not sticky, so a short screen scrolls and nothing lies over the content. "Bericht kopieren" belongs to the content, above, because it is rarely needed.
- **Sending screen.** `SendingScreen` in `ui/src/screens/` shows from the moment `print()` starts until the submit answers: after Drucken in "Jetzt drucken?", "Nochmal drucken?" and on "Erneut versuchen". Its screen state in `App.tsx` holds the running `upload` while the phone's copy is uploaded again, and then the `draftId` being submitted. The `Match` is not keyed, so the same screen goes on from one to the other.
  - The heading says "Wird hochgeladen … n %" during the upload, from the `Upload`'s progress as on the options screen. During the submit the screen reads `GET /api/drafts/:draftId/progress` with `readSubmitProgress()`, with a timeout chain, 500 ms after each answer. `preparing` reads "Wird vorbereitet …", with "Blatt x von y" and a bar when the Print Job has more than one sheet; x is the sheet being prepared, `sheetsDone + 1` and at most `sheets`. `sending` reads "Wird an den Drucker geschickt …". Before the first answer, and after a read that fails or a 404, it reads "Wird vorbereitet …". Once it has said `sending` it stays there, because a submit never goes back to preparing.
  - "Abbrechen" shows during the upload and while the Print Job is prepared, and goes once it is `sending`. During the upload it stops the upload. While preparing it calls `stopSubmit()`, `POST /api/drafts/:draftId/stop`, and the button stays off until the server answers. With a 204 the submit then fails with 409 `stopped`, which `print()` catches before "Drucken hat nicht geklappt". A 409 `not-stoppable` means the job is being sent: the screen switches to "Wird an den Drucker geschickt …" and the submit ends as always, on the status screen or on "Drucken hat nicht geklappt".
  - **Where Abbrechen leads.** When printing started on the options screen, `print()` got that screen's state as `from`, and goes back to it with the Print Options just sent as `initial`. Its upload and draft are unchanged, because a stopped submit leaves the draft as it was, so Drucken there sends the same draft again. After "Nochmal drucken" or "Erneut versuchen" there is no options screen to go back to, so `openHeld(options)` opens a new one with them, and uploads the phone's copy again.
  - While it shows, `filesHeld` is still set and `chosen` holds what was sent, so a 401 brings the person back to the options screen with those Print Options after the login, as from the options screen.
- **Status screen.** It assumes Wartet until the first answer. It polls with a timeout chain, 2 s after each answer, and stops once `endedAt` is set. The running timer counts from `since`, the time the job was sent by the phone's clock. "gedauert" is `endedAt - sentAt` from the server. The 60 s hint shows while the state is Wartet and the timer is at 60 s or more. Every ended state offers "Schließen" and "Nochmal drucken". The screen shows `reason` in every state that has one. Fehler adds "Details" with `ui/src/controls/Collapsible.tsx`. That is a button with `aria-expanded`, and the content is in the page only while open.
- **Abbrechen on the status screen** shows while the state is Wartet or Wird gedruckt and calls `cancelJob()`. While it is Wird gedruckt, a muted line right above it says "Was der Drucker schon hat, kann noch herauskommen.", because CUPS can't take back what the Printer already has. When the server refuses because the job has ended meanwhile, the next poll shows where it is.
- **Nochmal drucken** asks first. It opens the dialog "Nochmal drucken?" with `Dialog`, a sheet at the bottom edge as "Jetzt drucken?", and makes the screen behind it `inert`. Its lines come from the last `JobStatus`: `file.kind`, `options` and `sheets`, for example `4 Fotos (je 2×; Passbild) × 1 Kopie = 1 Blatt` and `Farbe · A4 · Füllen`, with the words of `job-text.ts`. It names the pages left out, "je 2×" when every printed one prints as often, and the layout unless it is Normal. The percentage of Einpassen and Füllen is not known there, so they stand alone. "Abbrechen" closes it, and its "Drucken" calls `onPrintAgain`. The status screen state in `App.tsx` keeps `options`. `print(options)` without an options screen uploads the phone's copy into a new draft and submits it with the same Print Options, without going back to the options screen.
- **"Drucken hat nicht geklappt".** Anything that throws inside `print()` in `App.tsx` leads to `SendFailedScreen`, except a stop by Abbrechen. That covers upload and submit, an error status and no network. Its screen state keeps `options`. "Erneut versuchen" calls `print(options)` without an options screen, so the phone's copy is uploaded into a new draft, as with "Nochmal drucken". "Schließen" calls `leaveJob()`. Some screens must come before it for one kind of failure, such as the expired login. Such a screen has to catch that failure first.

### Expired login

- **Where a 401 is noticed.** `call()` and `upload()` in `ui/src/api.ts` notice it for every API call, whoever makes it. They tell the listener `App` set with `onLoginExpired()` and then fail as any other error status does. So a new API call needs nothing extra to lead to "Anmeldung abgelaufen". Its caller still gets the rejection and has to catch it. Use `isLoginExpired(failure)` where a 401 must not end on a screen of its own, as `print()` does for "Drucken hat nicht geklappt".
- **"Anmeldung abgelaufen"** is not one of the screens of `Screen`. `App` has the signal `loginExpired`, and its `Match` is the first in the `Switch`. So it covers whatever screen shows and unmounts it, and the status screen stops polling. It never goes away again. The only way on is the page load of "Neu anmelden".
- **Session check.** `App` calls `GET /api/session` every time it opens, beside whatever else the opening does. Only a 401 matters, and `App` ignores any other failure.
- **"Neu anmelden"** loads `/login`, from `shared/login.ts`. The service worker answers `/` from its cache, so the app's own address never reaches Cloudflare. `/login` always goes to the network. Cloudflare Access shows its login for it and sends the browser back to it afterwards. The server answers it with a 303 to `/?logged-in=1`, in `server/http/session.ts`. On the Household network there is no Cloudflare and no 401.
- **What survives the login.** The files are the phone's copy. The rest is `interruptedJob` in `ui/src/interrupted-job.ts`, one `localStorage` record under `print-buddy.interrupted-job`. It holds the Print Options the person last tapped "Drucken" with. On the status screen it also holds the Print Job and when it was sent.
  - `App` writes it when "Anmeldung abgelaufen" appears on the status screen, or while the phone holds the files of a job. That state is `filesHeld`, from a share or "Datei auswählen" until `leaveJob()` or a Refusal.
  - `App` takes it out on every open and uses it only when the address says `logged-in`, so it never outlives one page load.
  - `leaveJob()` also forgets the Print Options last sent.
- **Print Options are known to `App` while the options screen shows**, through `onChange`, because the background upload can meet a 401 after the person changed something. A 401 during the upload brings the person back to the options screen with what they had chosen.
- **Where the person lands after the login.**
  - If the login ran out on the status screen, the person lands on the status screen of the same Print Job. Nothing is uploaded. `StatusScreen` takes `since`, so "läuft seit" and the 60 s hint go on from when the job was sent.
  - If it ran out anywhere else in a job, the phone's copy is uploaded into a new draft. The options screen opens with `initial`, the Print Options to start with in place of the starred Preset. This covers a share that just came in, an upload, "Drucken", "Nochmal drucken" and "Erneut versuchen".
  - If no job was in progress, the person lands on Start. This covers Start, "Bitte nochmal teilen", and the Refusal screen, where "Bericht kopieren" asks the server.
  - If the person closed the app on "Anmeldung abgelaufen" and opens it again, that is an open without a share. So the job is forgotten like any other.
- **"Bitte nochmal teilen"** is `ShareAgainScreen`, with "Datei auswählen". `openHeld()` and `uploadHeld()` go there whenever the phone holds no files. That happens after the login, after a share, and for "Nochmal drucken" and "Erneut versuchen".
- **No "Bericht kopieren" on "Anmeldung abgelaufen".** The spec lists the screens that have it, and this one is not among them. An expired login is no fault to report, and the report could not ask the server anything.

### Report

- **Report builder.** It is `ui/src/report.ts`. `buildReport(input)` is a pure function that makes the text. `copyReport(subject)` reads what it needs and writes the clipboard. A `ReportSubject` is either `{ job }`, the two numbers from submit, or `{ happened, files, options? }` for a report without a Print Job. `happened` is one German sentence. `files` is a function, called when the report is made.
- **Where the facts come from.** For a Print Job, the report reads everything from the server when the button is tapped.
  - `GET /api/jobs/:jobId` asks CUPS, so the state is live.
  - `GET /api/report` answers `ReportFacts`, the Print Buddy version and the Printer's state now.

  For this, `JobStatus` carries `file` and `options`. `file` has `kind`, `bytes` and `count`, the pages of the PDF or the photos in the job. Submit stores both in `job.json`. A server that doesn't answer doesn't stop the report. The report then says "unbekannt (Server nicht erreichbar)".
- **No file name.** Of the phone's files the builder reads only `type` and `size`. A new line in the report must not come from a `File`'s name, from file contents or from an error message the browser made up. See [ADR 0005](adr/0005-nothing-personal-is-kept.md). The report writes the Print Options with their keys as they are in `shared/print-options.ts`, so a new option shows up by itself.
- **The button.** It is `<ReportButton subject={…} />` in `ui/src/controls/`. It says "Kopiert", or "Kopieren hat nicht geklappt" when the browser refuses the clipboard, in an element with role `status`. A new screen where something can go wrong adds this one line with a `{ happened, files }` subject.
- **Send failures.** The `send-failed` screen state keeps what `print()` caught as `error`. `sendFailure(error)` in `report.ts` turns it into the sentence. The Refusal screen state keeps the refused `file`, because the phone's copy is cleared on a Refusal.
